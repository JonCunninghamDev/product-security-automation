# Product Security Automation Platform — Architecture

Status: Draft v0.1  
Date: 2026-09-03  
Specification: `ai/spec.md`

## 1. Architecture goal

The first release should prove a small number of security invariants clearly rather than simulate an enterprise security platform.

The system is built around one core rule:

> A release decision is deterministic, evidence-driven, and cryptographically verifiable. AI may explain the evidence but cannot change the decision or exercise signing authority.

The architecture therefore separates four concerns:

1. artifact and evidence generation;
2. deterministic policy evaluation;
3. privileged signing and independent verification;
4. advisory AI explanation.

## 3. Trust boundaries

### TB-1 — Untrusted artifact boundary

Anything submitted as an artifact, manifest, filename, metadata field, SBOM input, or user-provided description is untrusted.

Required controls:

- bounded input sizes;
- explicit Pydantic models for structured input;
- artifact content identified by SHA-256 digest;
- no shell interpolation from artifact metadata;
- artifact metadata never treated as trusted AI instructions.

### TB-2 — Evidence boundary

Security evidence is generated by deterministic tools and normalized into explicit internal models.

Examples:

- artifact digest;
- test result;
- SBOM;
- vulnerability finding summary;
- certificate status;
- signature verification result.

Raw tool output may be preserved as evidence, but policy decisions should consume normalized fields rather than scrape human-readable console text.

### TB-3 — Policy boundary

The policy engine is authoritative for release eligibility.

It receives immutable artifact identity plus normalized evidence and produces:

- `PASS` or `FAIL`;
- machine-readable reason codes;
- human-readable deterministic explanations;
- policy version;
- evaluation ID.

No AI output is accepted as policy input.

### TB-4 — Signing boundary

Signing is privileged and isolated from the normal API and AI assistant.

The signer may act only when presented with a valid, current policy evaluation for the exact artifact digest.

The signer must fail closed when:

- the decision is not `PASS`;
- the artifact digest differs from the approved digest;
- required signing identity/configuration is unavailable;
- the request attempts to bypass normal policy evaluation.

The local demo may use a development key, but private signing material must be generated outside Git history and excluded from source control.

### TB-5 — Verification boundary

Verification is independent of policy evaluation and signing.

A signed artifact is not considered release-ready until an independent verification step proves:

- the artifact content matches the signed identity;
- the signature is valid;
- the signing identity is trusted under the configured demo trust policy;
- applicable certificate validity checks succeed.

### TB-6 — AI boundary

The AI assistant receives a sanitized, read-only evidence projection.

It can:

- summarize failures;
- explain certificate/signature state;
- suggest remediation;
- produce a release-readiness narrative.

It cannot:

- invoke the signer;
- issue or revoke certificates;
- alter policy;
- write authoritative audit records;
- change a deterministic decision;
- receive private key material or credentials.

AI text is always labeled advisory.

## 4. Core workflow

### Happy path

1. A sample artifact is created.
2. The intake layer calculates SHA-256 and assigns an evaluation ID.
3. Evidence generation runs tests, SBOM generation, vulnerability/security checks, and required metadata validation.
4. Evidence is normalized into a policy input model.
5. The policy engine returns `PASS` with explicit reason codes.
6. The signing service receives the approved artifact digest and signs the artifact through the isolated signing path.
7. An independent verifier validates artifact integrity, signature, and trust material.
8. The system writes an audit record containing the inputs, policy version, decision, signing identity metadata, and verification result.
9. The AI assistant receives only the sanitized audit/evidence projection and generates an advisory summary.

### Tamper path

1. A previously evaluated or signed artifact is modified.
2. Its SHA-256 digest changes.
3. Verification against the recorded/signed identity fails.
4. The deterministic release state is `FAIL` regardless of any AI-generated explanation.

### Unauthorized signing path

1. A caller requests signing without a valid passing evaluation for the artifact digest.
2. The signing boundary rejects the request.
3. The rejection is recorded as security-relevant audit evidence.

## 5. Initial component model

### `artifact`

Responsibilities:

- calculate SHA-256;
- model artifact identity;
- validate submitted file metadata;
- prevent post-evaluation digest substitution.

### `evidence`

Responsibilities:

- ingest normalized results from tests/scanners/SBOM tooling;
- preserve references to raw evidence;
- produce a stable policy input model.

### `policy`

Responsibilities:

- deterministic rules only;
- versioned policy definition;
- reason codes;
- stable results for identical inputs.

Initial reason-code examples:

- `ARTIFACT_DIGEST_MISMATCH`
- `REQUIRED_EVIDENCE_MISSING`
- `VULNERABILITY_THRESHOLD_EXCEEDED`
- `CERTIFICATE_UNTRUSTED`
- `CERTIFICATE_EXPIRED`
- `SIGNATURE_INVALID`
- `POLICY_PASS`

### `pki`

Responsibilities:

- create local development trust material;
- issue demo certificates;
- expose certificate metadata;
- validate trust and expiry behavior;
- demonstrate documented invalidation/revocation behavior.

This is explicitly a learning/demo CA, not a production CA implementation.

The bounded development implementation uses one ephemeral self-signed root and
directly issued leaf certificates. Trust is an explicit allowlist of exact root
certificate fingerprints. Its invalidation strategy is to remove a root from that
allowlist and regenerate the ephemeral CA and leaves. Certificate revocation lists,
OCSP, intermediate CAs, and persistent CA key custody are intentionally outside this
increment; they must be added through a later decision before production use is
represented.

Private keys are generated in process memory. Persistence is opt-in, encrypted, and
written only with owner-only permissions. Generated key paths and common private-key
suffixes are excluded from Git.

### `signing`

Responsibilities:

- enforce authorization based on exact artifact digest + passing evaluation;
- call established signing tooling;
- never expose private key material;
- return signature/bundle metadata.

### `verification`

Responsibilities:

- independently verify signed artifacts;
- validate artifact identity and signing trust;
- produce normalized verification evidence.

### `audit`

Responsibilities:

- record evaluation ID, artifact digest, policy version, checks, decision, signer metadata, verification result, timestamps, and evidence references;
- exclude credentials and private key material;
- make demo records easy to inspect and diff.

For v1, a local JSONL or structured-file audit store is acceptable if writes are controlled and the limitations are documented. A production append-only store is out of scope.

### `assistant`

Responsibilities:

- consume sanitized evidence only;
- generate advisory summaries/remediation;
- degrade deterministically when no model is available.

## 6. Tooling direction for v1

The project will prefer established tools over custom security implementations.

### PKI learning/demo layer

Use Python's `cryptography` package for X.509 certificate creation/inspection in the local development PKI layer. This keeps PKI behavior visible in Python while relying on established cryptographic primitives.

### Artifact signing

Use Sigstore Cosign for artifact/blob signing and independent verification. Cosign supports file/blob signing, verification bundles, identity-based signing, self-managed keys, and KMS-backed keys. The local-first path should not require an external account; CI/cloud identity-backed signing can be added as a separate demonstration path.

### SBOM

Use Syft to generate an SPDX or CycloneDX SBOM from the project/artifact.

### Vulnerability evaluation

Use Trivy to evaluate SBOM or project vulnerability evidence and normalize relevant results for policy evaluation.

Tool invocation is an integration concern. The policy engine must not depend on fragile parsing of arbitrary terminal prose.

## 7. Local key-handling model

The first demo will maintain a hard separation between repository content and generated secret material.

Expected local structure:

```text
.runtime/             # gitignored
  pki/
    root-key.pem
    root-cert.pem
    signer-key.pem
    signer-cert.pem
  evidence/
  audit/
```

Rules:

- `.runtime/` is never committed;
- private key files are generated locally;
- demo setup is reproducible from commands/scripts;
- tests may use ephemeral keys generated inside temporary test directories;
- committed fixtures may include public certificates or deliberately non-secret test material only when clearly labeled.

## 8. Audit model

A first-version audit record should resemble:

```json
{
  "evaluation_id": "...",
  "artifact": {
    "sha256": "...",
    "name": "sample-artifact"
  },
  "policy_version": "v1",
  "checks": [
    {"code": "SBOM_PRESENT", "status": "pass"},
    {"code": "VULNERABILITY_GATE", "status": "pass"}
  ],
  "decision": "PASS",
  "signing": {
    "identity": "demo-product-signer",
    "artifact_sha256": "..."
  },
  "verification": {
    "signature_valid": true,
    "trusted": true
  },
  "created_at": "..."
}
```

The schema should become a Pydantic model and receive explicit schema/version handling before v1 is considered complete.

## 9. Threat-to-control mapping

| Threat | Primary control |
| --- | --- |
| Artifact tampering | SHA-256 identity + independent signature verification |
| Unauthorized signing | isolated signer + passing evaluation bound to exact digest |
| Signing-key leakage | keys outside Git + least-access local boundary + optional KMS path |
| Expired/untrusted cert | explicit X.509 validation tests and policy evidence |
| Malformed input | typed models, bounds, no shell interpolation |
| CI credential exposure | minimal secrets, least privilege, no secret output |
| Dependency compromise | SBOM + vulnerability scanning + pinned/controlled CI dependencies |
| Audit alteration | controlled writer, digest/evidence correlation, limitation documented for local demo |
| Prompt injection | sanitized evidence projection; artifact text never becomes instructions |
| AI hallucination | advisory labeling + deterministic decision independent of AI |

## 10. API boundary

FastAPI should be introduced only where it makes the trust boundaries easier to demonstrate.

Likely v1 endpoints:

- `POST /evaluations` — submit or reference a sample artifact and create deterministic evaluation;
- `GET /evaluations/{id}` — inspect decision and evidence;
- `POST /evaluations/{id}/sign` — privileged demo signing request that re-validates authorization;
- `POST /verify` — independently verify artifact/signature material;
- `GET /evaluations/{id}/advisory` — advisory AI/fallback explanation.

The CLI/demo script may call the same application services directly so the security model does not depend on HTTP.

## 11. Implementation sequence

Implementation should follow this dependency order:

1. define Pydantic domain models and reason codes;
2. implement artifact hashing and tamper tests;
3. implement development PKI lifecycle and trust/expiry tests;
4. implement deterministic policy engine;
5. integrate Cosign signing/verification behind adapters;
6. add audit records;
7. integrate Syft/Trivy evidence adapters;
8. add CI security gates;
9. add AI advisory layer and fallback;
10. create the three-minute demo and evidence index.

The first implementation pull request should not attempt all ten steps. Each change should leave behind executable evidence for the invariant it introduces.

## 12. Production-oriented extension path

After the local portfolio release works, an optional AWS path may demonstrate:

- AWS KMS asymmetric signing key;
- least-privilege IAM role for signer access;
- S3 object-version/digest correlation;
- DynamoDB or immutable-object audit metadata;
- EventBridge/SQS workflow separation;
- Bedrock advisory explanation using the same read-only evidence projection.

The local deterministic interfaces should remain unchanged so cloud services are adapters, not sources of product policy.

## 13. Architecture acceptance criteria

Architecture is ready for implementation when:

- trust boundaries are explicit;
- AI cannot reach signing/authorization capabilities;
- signer authorization is bound to an exact artifact digest;
- independent verification is required after signing;
- audit evidence schema is defined sufficiently for first tests;
- PKI/signing tools are established rather than custom cryptography;
- local secret material is explicitly separated from Git;
- first implementation sequence is small enough to test incrementally.
